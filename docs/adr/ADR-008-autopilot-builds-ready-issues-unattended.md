# ADR-008: Autopilot builds ready issues unattended

- **Decision:** An hourly T3 Code scheduled task starts a fresh T3 Code thread that runs `/engineering:autopilot-t3`, which builds each ready issue in a child thread, one at a time, answers each child's questions, merges sub-issue PRs that verify marked ready, starts ship, and hands only PRs into `main` and stuck issues to the user with one comment.
- **Builds on:** [ADR-001](ADR-001-github-is-the-work-state-store.md), [ADR-004](ADR-004-skills-load-on-demand-scripts-fetch-facts.md), [ADR-006](ADR-006-engineering-runs-in-cloud-sessions.md)
- **Source:** [#224](https://github.com/cstalhem/cargus-forge/issues/224), [#262](https://github.com/cstalhem/cargus-forge/issues/262), [#265](https://github.com/cstalhem/cargus-forge/issues/265), [#368](https://github.com/cstalhem/cargus-forge/issues/368)

## Details
- **Shape stays with the user.** Autopilot runs neither discuss nor slice, and leaves requests alone. It starts at a ready issue, one with a `## Scenarios` section and no open blocker, and ends at a PR into `main`: a single issue's PR or a final PR, which the user reviews and merges. The exception is the fix sub-issues of an anneal, which [ADR-010](ADR-010-anneal-shapes-fixes-without-discuss.md) covers: anneal writes them as ready issues without discuss.
- **A typed skill, and the one Autopilot.** `autopilot-t3` has `disable-model-invocation: true`, so it costs no context until typed, and the scheduled task's prompt is exactly `/engineering:autopilot-t3` ([ADR-004](ADR-004-skills-load-on-demand-scripts-fetch-facts.md)). It checks no surface: T3 injects the `t3-code` MCP server into every provider session, and the skill loads each `t3-code` tool through `ToolSearch` where a step first needs it, so a thread whose tool does not load stops there.
- **The T3 pieces.** An hourly T3 scheduled task, created from a run after the user's yes with `schedule_task` and `bindToCurrentThread` false, starts each run as a fresh thread in its own worktree from the project's base ref; it inherits the creating thread's model, runtime mode and interaction mode, so the user runs the first `/engineering:autopilot-t3` on the model and in the mode they want for the hourly run and each ship child. `list_scheduled_tasks`, `t3_thread_list`, `t3_thread_read` and `t3_pending_request` read the facts; a child is a thread titled `execute #<n>` or `ship #<u>`, working when its run is active and no request is pending, and its answers are counted by the `Autopilot: answer` prefix in its user messages. A run learns its own thread id from `t3_thread_update` `rename`, which names it `autopilot <ISO timestamp>` at the same time. The hourly run works in a fresh worktree, not the project root, because `status.sh` reads git in the current directory and T3's worktree cleanup removes settled worktrees.
- **No state of its own.** Each run reads the facts: the project's scheduled tasks and threads through the `t3-code` tools, each issue's status through `status.sh` ([ADR-001](ADR-001-github-is-the-work-state-store.md)), and hand-offs as comments on the issue or the PR. The threads titled `execute #<n>` or `ship #<u>` are the claim on an issue, whatever the thread's state.
- **One child at a time**, sub-issues in blocked-by order. Each child is launched with `t3_thread_launch` in its own worktree from `main` with `startFromOrigin` true, in `full-access` mode, with a `clientRequestId` from its title so a retried launch returns the same thread. Its first message is the typed `/engineering:execute #<n>` or `/engineering:ship #<u>`, so execute keeps its required argument and `disable-model-invocation`. The report instruction is a second, queued message right after the launch, because `t3_thread_launch` has no system prompt field and text after the typed command would become the skill's `$ARGUMENTS`. When its work ends, for any reason except a turn that ends on a resume that the skill scheduled itself, such as execute's PENDING resume, the child sends one message to Autopilot's thread, `<title>: finished`, `<title>: stopped on a question` or `<title>: stopped: <reason>`, with the PR and, for a question, its recommended answer. The child's `t3_thread_send` to the idle run thread starts the next run. A turn that ends on a scheduled resume sends none, so the child keeps its claim and Autopilot posts no hand-off for slow CI.
- **The plugin on the host.** A child loads the engineering plugin from the host's installed copy, never from the checkout's skill files. The plugins synced from claude.ai do not reach a thread that T3 starts. A run checks `claude plugin list` before it starts a child, and a child whose typed prompt did not load as a skill reports `<title>: stopped: engineering plugin not loaded in this environment` and does nothing else.
- **Answers.** Autopilot answers a child with the child's recommended answer, or with the answer that changes no scenario and no decision of the issue, at most three times. Each answer goes through the child's pending request, when one is listed, and a queued message that starts with `Autopilot: answer <k> of 3`, so a run counts the answers in the child's messages. execute records each answer under the PR's `## Deviations` as `Autopilot: <question> → <answer>, because <why>`, and ship gathers those lines into the final PR, so the user reads them at review.
- **Merges.** Autopilot squash-merges a sub-issue PR once verify has marked it ready ([ADR-002](ADR-002-feature-branch-per-umbrella.md)). When a child's verify passed but could not mark the PR ready, because the permission was denied in the child, Autopilot marks it ready itself first. It merges no single-issue PR and no final PR. execute, verify and ship merge nothing, as before, so a Build skill run by hand changes nothing about who merges.
- **Hand-offs.** There are three: a child that asks a fourth question after three answers; a child that stopped for another reason, such as execute sending a single issue back to discuss or the plugin not loading in the child; and a single issue's PR or a final PR that is ready for review. Each is one comment, `Autopilot: stopped, <why>` on the issue or `Autopilot: ready for your review` on the PR, and no push of its own, because T3 Connect pushes when a thread finishes, fails or asks. Children run in `full-access` mode, so no child waits on a permission prompt. The comment is the record, so a run hands the same thing off only once.
- **Models.** An execute child runs on the current Sonnet model of the inherited provider instance, which the run reads from `orchestrator_capabilities`, and a ship child inherits the run's model, which is the scheduled task's. execute, and the verify it calls, run on Sonnet in that child, because execute is nearly all the tokens and a sized sub-issue does not need the strongest model.
- **The hourly run is the backstop.** A lost report or a missed answer waits at most one hour, because the next run reads the same facts and the same threads.
- **The scheduled task** is `engineering: autopilot`, an interval of 3600000 ms, a fresh thread each firing. The read-back checks that one task has the prompt `/engineering:autopilot-t3`. The user pauses or deletes it in T3's scheduled tasks list. A run reports a paused task or a `blockedByPolicy`, and changes an existing task never.
- **No trial run.** The first real issue Autopilot builds is its test, and what it shows broken becomes a new issue.

## Rejected alternatives
- **A cloud Autopilot beside the T3 one:** no session runs in the cloud, and every shared step was written twice.
- **Shape over issue comments:** discuss and slice are questions and yes gates, so an unattended run saves no work and needs a comment protocol, a waiting status and an event trigger.
- **One hourly run per sub-issue:** an umbrella would take days.
- **Parallel children:** sub-issues touch the same `plugin.json` and skill files, and execute never merges the feature branch into a sub-issue branch.
- **A bare `/engineering:execute` that picks the first ready issue:** a scheduled task's prompt holds one command, and the orchestration then lives in execute.
- **One persistent Autopilot thread:** it needs a manual start, must survive forever and compacts over months, while a fresh thread reads every fact from the service.
- **Polling children:** a queued report instruction makes the child report when its turn ends.
- **A claim label on the issue:** it copies the thread list and goes stale when a child dies before its PR, which needs a repair step.
- **A child that follows the skill file from the checkout when its typed prompt did not load:** it works only in the plugin's own repo, and it bypasses `$ARGUMENTS`, the injected rules and `allowed-tools`, so the child runs an untyped copy of the skill.
- **One model for every phase:** execute is nearly all the tokens, and a sized sub-issue does not need the strongest model.
- **A model per phase in the scheduled task:** a scheduled task holds one model, so the routing has to live where the child is started.
- **`delegate_task` children on T3:** a delegated child shares the parent's branch and worktree and takes no workspace strategy, so an execute child would switch the parent's checkout.
- **Create the T3 scheduled task in the settings UI:** the MCP path inherits the model and the modes from the creating thread and keeps the first run's proposal, so no settings are typed by hand.
- **The project root as the hourly run's workspace:** `status.sh` reads git in the current directory, and T3 removes settled worktrees on its own.
- **The report instruction in the launch message:** text after the typed command becomes the skill's arguments.
- **A child reports on every turn end:** Autopilot hands off and releases the claim of a child whose scheduled resume is still due.

## Consequences
- The user shapes requests in discuss and reviews PRs into `main`. Everything between runs unattended, and the plugin still works without Autopilot.
- A sub-issue PR reaches the feature branch with no human review. The review happens on the final PR, which gathers every deviation and every answer Autopilot gave.
- A child that needs a human waits for the user, and the issue's comment names the thread to open.
- The scheduled task starts a thread every hour, which costs tokens even when the run finds nothing to do.
- The scheduled task is created from a run after the user's yes, never in T3's settings UI.
- A sub-issue is built and graded on Sonnet. A sub-issue that needs the strongest model is run by hand with `/engineering:execute #<n>` in a thread on that model.
- The plugin must be installed on the T3 host, and children run in `full-access` mode with no approval prompt.
- A plugin bug that a child hits ends as a stopped issue with one comment, and becomes a new issue, not a silent retry loop.
