- Read only this plugin's files, the current repo's files, and GitHub data about the current repo, such as issues or branch protection, through `gh` calls that change nothing. Read `docs/adr/` and `docs/agents/` only if they exist.
- Add no labels.
- Write to GitHub with `gh` first. If a `gh` write is refused, such as an HTTP 403 from GraphQL or a proxy message that the path is not permitted, load the GitHub MCP tools with ToolSearch and do the same operation with the tool whose description fits it. Then use MCP for every other write in the run, and do not try `gh` again. If every `gh` write succeeds, call no MCP tool. If no GitHub MCP tool can do the operation, stop and name the refused write.
  - For `gh issue develop <n> --base <base> --name <n>-<slug>`, the same operation is to create the branch `<n>-<slug>` from `<base>`.
- Pass every issue body, PR body and comment to `gh` with `--body-file <path>`. First write the text with the Write tool to a new file in the session's scratchpad directory, else in the system temp directory (`$TMPDIR`, else `/tmp`). Never use a heredoc: Claude Code's worktree guard refuses one whose text mentions git. This rule is for `gh` only. Through MCP, put the text in the tool's text parameter, such as `body`.
- After each write to GitHub, on either path, read the result back with `gh api` REST, for example `issues/<n>/parent` for a sub-issue's parent, `pulls/<n>` for a PR's base and draft state, `issues/<n>/comments` for a posted comment, and `branches/<branch>` for a created branch. If a fact the step needs is missing, stop and name it.
