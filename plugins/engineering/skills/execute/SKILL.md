description: Take one ready issue to a draft PR, in the session's worktree locally, or in the current directory in a cloud session, on its designated branch if it names one. Gets onto the issue branch, builds until the issue's verify command passes, adds the rules and the checks that the work proved, opens the draft PR, then calls verify.

# execute

Issue: $ARGUMENTS

## Rules
!`cat "${CLAUDE_PLUGIN_ROOT}/references/rules.md"`
- Locally, use the session's worktree. Do not make a second one, and do not move or rename its directory, because that breaks the running session. In a cloud session, enter no worktree. Use the designated branch if the session names one, and otherwise the issue's `<n>-<slug>` branch, in the current directory. A session is a cloud session when `printenv CLAUDE_CODE_REMOTE` prints `true`.
- Run plain git commands, one at a time, in the current directory: no `cd … &&` and no `git -C`. Claude Code blocks git commands that it cannot confirm stay inside the worktree.
- The arguments are `#<n>`, with a `PENDING resume <k> of 3` suffix when step 7 of an earlier run in this session scheduled this run with `send_later` or `schedule_task`. The suffix changes nothing before step 6.
- Deviations:
  1. A bug in the way of the issue: fix it, and name the fix in the PR.
  2. A missing guard that the issue needs: add it, and name it in the PR.
  3. A broken check or tool that blocks the issue: fix it.
  4. A change to the architecture or to a scenario: stop and ask. A change that makes an ADR false, and that no `ADR` decision covers, is a change to the architecture.
  5. The issue fails the size test: stop. Name the criterion that fails and what you found. Commit the work so far and push it as step 3 says. Then:
     - a sub-issue: the draft PR stays open. A later run on the narrowed sub-issue resumes from this PR in a session with a designated branch, and from the issue branch otherwise. Call the Skill tool with `engineering:slice`, `#<n>` and the failing criterion with your findings. After slice ends, tell the user to run `/engineering:execute #<n>` again.
     - a single issue: close the draft PR that the push found or opened with `gh api -X PATCH repos/{owner}/{repo}/pulls/<pr> -f state=closed`, and read it back with `gh api repos/{owner}/{repo}/pulls/<pr>` to check that its `state` is `closed`. Its branch becomes the feature branch, so no PR stays open. Tell the user to run `/engineering:discuss #<n>`, which turns it into an umbrella issue.
  6. A new domain name that the code needs and that no `Term` decision and no glossary entry covers, or a rename of a domain name: if it passes the gate in `domain-model.md`, add or edit its entry in `docs/glossary.md` in the same PR, as `domain-model.md` says, and name the entry under the PR's `## Deviations`.
- An answer from another session: when a step says to stop and ask, and the answer arrives as a message from another session, such as Autopilot's, instead of from the user, go on from that answer as if the user gave it. Record it in the PR under `## Deviations`, as the PR body format of `formats.md` says, with the question you asked, the answer the message gave and the reason it gave, so the user reads the answer at review.

## Steps
1. **Load.** Read `${CLAUDE_PLUGIN_ROOT}/references/size-test.md`, `${CLAUDE_PLUGIN_ROOT}/references/formats.md`, `${CLAUDE_PLUGIN_ROOT}/references/issue-tracker.md` and `docs/agents/commands.md`. Run `gh api repos/{owner}/{repo}/issues/<n>`, `gh api repos/{owner}/{repo}/issues/<n>/parent` and `gh api 'repos/{owner}/{repo}/issues/<n>/dependencies/blocked_by?per_page=100'`. Stop and say why if the issue is closed or has no `## Scenarios` or `## Verify` section. Read `${CLAUDE_PLUGIN_ROOT}/references/domain-model.md` every time, not only when a term comes up, and follow its `In execute` section. Read `${CLAUDE_PLUGIN_ROOT}/references/adr.md` every time too, not only when the issue has an `ADR` decision, and follow its `In execute` section.
   - **Repo profile:** if the repo has no `docs/agents/commands.md`, tell the user to run `/engineering:setup`, which writes it, and go on with the issue's Verify command as the only check.
   - **Base:** for a sub-issue, the parent's feature branch: the one branch that `git ls-remote --heads origin 'refs/heads/<parent>-*'` lists, by the branch pattern in `references/issue-tracker.md`. Stop if it lists none, or more than one. For a single issue, `main`, the default branch.
   - **Blockers:** read the issue's blockers, and their state, from its `dependencies/blocked_by` links only. If an open issue blocks a single issue, stop. If one blocks a sub-issue, list the merged PRs into the base with `gh api 'repos/{owner}/{repo}/pulls?base=<base>&state=closed&per_page=100' --jq 'length, (.[] | select(.merged_at) | {number, body})'`, page by page as the rules say. A repo without the close-sub-issue workflow leaves a merged sub-issue open, so an open blocker counts as merged when a merged PR's first line names it as its issue ("Sub-issue #<b> of"). A mention elsewhere in a body does not count. Name each such PR and go on. Stop and name each open blocker that has no such PR.
   - **Decisions:** the issue's `Term` and `ADR` decisions are its own `D<n> · Term:` and `D<n> · ADR:` lines, and each `#<umbrella> D<n>` line in its `## Decisions` whose decision in the umbrella is a `Term` or an `ADR` decision. Read that decision's text in the body that the `/parent` call returns.
2. **Worktree.** Run `git rev-parse --abbrev-ref HEAD`, `git rev-parse --absolute-git-dir`, `git rev-parse --path-format=absolute --git-common-dir`, `git status --porcelain`, `git rev-list HEAD --not --remotes`, `printenv CLAUDE_CODE_REMOTE` and `git ls-remote --heads origin 'refs/heads/<n>-*'`, which lists the issue's branch. The session is in a worktree when the git dir and the common dir differ. Also check whether the `orchestrator_capabilities` tool (`mcp__t3-code__orchestrator_capabilities`) is in your tools, as a tool listed as deferred counts, and load nothing: the session is then a T3 Code thread, which step 7 uses.
   - **Sync:** the cases below that say "sync" run these on the issue branch `<branch>`:
     1. Run `git fetch origin <base> <branch>`. If it fails, for example because `<branch>` is not on the remote, stop and ask.
     2. Run `git rev-list --left-right --count HEAD...origin/<branch>`, which counts the commits only on `HEAD` and only on `origin/<branch>`. If they have diverged (both counts above 0), stop and ask. If `HEAD` is behind `origin/<branch>`, run `git merge --ff-only origin/<branch>`, and stop and ask if it fails.
   - **In a session with a designated branch it must push to** (a Claude Code cloud session names one in its system prompt): that branch is the issue branch, and the cases after this one do not apply. Enter no worktree and create no `<n>-<slug>` branch. Stop if `HEAD` is not on the designated branch. List its open PR with `gh api 'repos/{owner}/{repo}/pulls?head={owner}:<branch>&state=open&per_page=100'`.
     - **An open PR whose first line names #<n>** ("Sub-issue #<n> of" or `Closes #<n>`): resume. Stop and ask if the PR's base is not `<base>`. Sync as above. Then read `git log --oneline origin/<base>..HEAD` to see what is done.
     - **No open PR, with no changes and no commits that are not on a remote:** start the branch at the base, so the PR holds only this issue's work. Run `git fetch origin <base>`. If `git ls-remote --heads origin 'refs/heads/<branch>'` lists the branch, run `git fetch origin <branch>`, and stop and ask if `git log --oneline origin/<base>..origin/<branch>` shows commits. Then run `git reset --hard origin/<base>`.
     - **Anything else** (an open PR for another issue, changes, or commits that are not on a remote): stop, show what the branch holds, and ask.
   - **On the issue's branch:** resume. Sync as above. Then read `git log --oneline origin/<base>..HEAD` to see what is done.
   - **Not in a worktree, locally:** enter a new one with the EnterWorktree tool, then go on as in the next case.
   - **Not on the issue's branch, with no changes and no commits that are not on a remote:** `HEAD` is detached, on `<base>`, or on a branch whose name does not follow `<n>-<slug>`. In a cloud session, enter no worktree.
     1. If `git ls-remote` lists no branch for the issue, create `<n>-<slug>` from `<base>` as the rules say, with the branch pattern from `references/issue-tracker.md`.
     2. Sync as above, and run `git switch <branch>` between its fetch and its count. A local `<branch>` that already existed can be behind, and the count finds that. If `git ls-remote` listed the issue's branch, then read `git log --oneline origin/<base>..HEAD` to see what is done.
     3. If `HEAD` was on a branch other than `<base>`, run `git branch -D <that branch>`. It loses no commit, because every commit is on a remote, and git refuses to delete a branch that another worktree has checked out. `<base>` stays: it can be the feature branch from step 1, because discuss turned a single issue with work so far into an umbrella and the issue's own branch became the feature branch.
     4. Locally, ask the user to name the session with `/rename <branch>`.
   - **Anything else** (changes, commits that are not on a remote, another issue's branch, or a `git switch` that fails): stop, show what the checkout holds, and ask.
3. **Implement.** Read the code that the Files section names. Work one scenario at a time, and commit as you go with messages that say what changed and why. After the first commit, run `git push -u origin <branch>`. After each push, this one, deviation 5's and step 6's, look up the branch's open PR with `gh api 'repos/{owner}/{repo}/pulls?head={owner}:<branch>&state=open&per_page=100'`. If the branch has no open PR, open the draft PR right then with `gh api -X POST repos/{owner}/{repo}/pulls -f title="<issue title>" -f head=<branch> -f base=<base> -F draft=true -F body=@<path>`, with the first line of the PR body in `formats.md` and the line "execute rewrites this body at its PR step." as its body, written to a file as the rules say. Read it back with `gh api repos/{owner}/{repo}/pulls/<pr>`, and stop if its base is not `<base>`, it is not a draft, or its title or body is not the one you wrote. From then on the issue reads as in progress, and step 6 rewrites the PR. Follow the deviation rules. Write each `Term` decision into `docs/glossary.md` as `domain-model.md` says. The Glossary section at the end of this skill holds the file as it was when the skill loaded, and step 2 can switch or update the branch after that, so read `docs/glossary.md` on the issue branch, if it exists, before you judge that no entry covers a name, and before you write an entry. Write each `ADR` decision into `docs/adr/` as `adr.md` says. Read `docs/adr/` on the issue branch first, for the same reason.
4. **Check.** Run the issue's Verify command and each pre-PR check: each row of `docs/agents/commands.md` whose task ends with `(pre-PR check)`, and no other row. If `commands.md` has no such row, or does not exist, run only the Verify command. If one fails, go back to step 3.
5. **Reflect.** Ask what this work proved that a rule or a check should hold, once the checks pass. A proposal needs evidence from this run: a correction that you received, a failed check or verify gap that a rule or a check could have stopped, or a fact that you found twice. List each proposal with its evidence, and drop any that `.claude/rules/` on the issue branch already holds, that the repo's CLAUDE.md, AGENTS.md or CONTRIBUTING.md already says, or that a linter or formatter config that a pre-PR check runs already enforces. A proposal that one command can check is a check, as the rule test says: it is never dropped and never a rule. No evidence is the normal result for proposals: write none, and add nothing to the PR body for them. Reflect never waits for the user to add a check or file a request: the user reviews each check in the PR and shapes each request in discuss.
   - **Write the rule.** Add each proposal that one command cannot check as one line to `.claude/rules/<area>.md`, as the Repo rules section says. Create the file if it does not exist, with `paths:` frontmatter when the Repo rules section says so.
   - **Write the check.** Add each proposal that one command can check in the first form that fits: a test in a file that an existing pre-PR check runs, a rule in a linter or formatter config that an existing pre-PR check runs, or a new `(pre-PR check)` row in `docs/agents/commands.md` whose command already works in the repo. Commit the check with the work, then prove it: put the defect back with an edit, see the pre-PR check that runs the check fail, restore the file with `git checkout -- <file>`, check that `git status --porcelain` prints nothing, and see that pre-PR check pass.
   - **Or file a request.** When the check fits none of those forms, is too big for this PR by the size test, the repo has no `docs/agents/commands.md`, or no edit puts the defect back, create a request instead: an issue with no label and neither `## Scenarios` nor `## Goal`, that holds the lesson, its evidence and the proposed check. Read it back.
   - **Check each rule against the Repo rules section.** This covers each rule that the PR adds, the rules from this step and any rule that the issue's scenario carries, such as `WHEN .claude/rules/<area>.md is read THEN it holds <rule>`. Reword a rule that fails the rule test, and drop a proposal that cannot pass it. A rule that the issue's scenario carries and that cannot pass it is a change to a scenario: deviation 4.
   - **Write the skill, only when a rule needs it.** Decide by the Repo rules section whether each of those rules needs a backing skill. If one does, create or extend `.claude/skills/<name>/SKILL.md` as the Repo rules section says, and end each rule it backs with `(see skill: <name>)`.
   - **Commit and name it.** Commit the rules, skills and checks with the work that proved them. Under `## What it delivers` in step 6, add one bullet for each rule and each skill, naming its file and its evidence, one bullet for each added check, naming its file, its evidence and that it failed on the defect and passed after the fix, and one bullet `Request #<m>: <check>, with its evidence` for each request.
6. **PR.** Run `git push -u origin <branch>`. Step 3's lookup after this push gives the branch's draft PR `<pr>`, found or opened. Rewrite its title and body with `gh api -X PATCH repos/{owner}/{repo}/pulls/<pr> -f title="<issue title>" -F body=@<path>`. Write the body to a file as the rules say. Read the PR back with `gh api repos/{owner}/{repo}/pulls/<pr>`, and stop if its base is not `<base>`, it is not a draft, or its title or body is not the one you wrote. Write the body in the PR body format of `formats.md`.
7. **Hand off.** Call the Skill tool with `engineering:verify` and the PR number.
   - **FAIL:** fix each gap and each failed check that its report names, and go back to step 4. If it fails a second time, stop and ask.
   - **PENDING:** name each pending check. A PENDING verdict does not count as one of the two failures. Then, the first that applies:
     - **A resume left, in a cloud session or a T3 Code thread:** the session is a cloud session (step 2's `printenv CLAUDE_CODE_REMOTE` printed `true`), or it is not and step 2 found the `orchestrator_capabilities` tool in its tools, so it is a T3 Code thread. The arguments carry no `PENDING resume <k> of 3` or carry one with `<k>` below 3; `<k>` is 0 when they carry none. Schedule a run 10 minutes ahead with the title `execute #<n>: PENDING resume <k+1> of 3` and the prompt `/engineering:execute #<n> PENDING resume <k+1> of 3`, as below. Once it is scheduled, say that the run resumes itself in 10 minutes, and end the turn. The prompt starts a run in this session or thread that resumes on this branch and calls verify again, and its arguments carry the count, so at most three resumes follow one PENDING verdict after another.
       - **Cloud session:** call the `send_later` tool with `delay_minutes` 10, that title as its name and that prompt as its message.
       - **T3 Code thread:** load the `schedule_task` tool with the `ToolSearch` tool, query `select:mcp__t3-code__schedule_task`. Run `date -u -d '+10 minutes' +%Y-%m-%dT%H:%M:%SZ 2>/dev/null || date -u -v+10M +%Y-%m-%dT%H:%M:%SZ`, which prints the time 10 minutes ahead with GNU `date` or, failing that, BSD `date`. Call `schedule_task` with that title, that prompt, `schedule` `{"type": "once", "runAt": "<that time>"}` and `bindToCurrentThread` true. Check its result: it must show a `once` schedule with a `nextRunAt`. If the call fails, or the result does not, stop as in the next bullet and say that the host needs a T3 Code build with one-time scheduled tasks (v0.1.7, or a nightly from 2026-11-01 on). The spent task stays in T3's scheduled tasks list until T3 deletes it with its thread: delete none.
     - **Otherwise** (neither a cloud session nor a T3 Code thread, `schedule_task` failed, or the third resume got PENDING): stop. Tell the user to run `/engineering:execute #<n>` again once CI has finished. That run resumes on this branch and calls verify again.
