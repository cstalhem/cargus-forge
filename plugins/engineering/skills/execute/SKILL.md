# execute

Issue: $ARGUMENTS

## Rules
!`cat "${CLAUDE_PLUGIN_ROOT}/references/rules.md"`
- Locally, use the session's worktree. Do not make a second one, and do not move or rename its directory, because that breaks the running session. In a cloud session, enter no worktree. Use the designated branch if the session names one, and otherwise the issue's `<n>-<slug>` branch, in the current directory. A session is a cloud session when `printenv CLAUDE_CODE_REMOTE` prints `true`.
- Run plain git commands, one at a time, in the current directory: no `cd … &&` and no `git -C`. Claude Code blocks git commands that it cannot confirm stay inside the worktree.
- The arguments are `#<n>`, with a `PENDING resume <k> of 3` suffix when step 6 of an earlier run in this session scheduled this run with `send_later`. The suffix changes nothing before step 6.
- Deviations:
  1. A bug in the way of the issue: fix it, and name the fix in the PR.
  2. A missing guard that the issue needs: add it, and name it in the PR.
  3. A broken check or tool that blocks the issue: fix it.
  4. A change to the architecture or to a scenario: stop and ask. A change that makes an ADR false, and that no `ADR` decision covers, is a change to the architecture.
  5. The issue fails the size test: stop. Name the criterion that fails and what you found. Commit and push the work so far with `git push -u origin <branch>`. Then:
     - a sub-issue: the draft PR from step 3 stays open. If the branch has no open PR, open a draft PR as in step 5, with the same title, first line, base and read-back. Its body is the first line and one line that names the failing criterion. A later run on the narrowed sub-issue then resumes, from this PR in a session with a designated branch and from the issue branch otherwise, and its step 5 rewrites the PR's title and body. Then call the Skill tool with `engineering:slice`, `#<n>` and the failing criterion with your findings. After slice ends, tell the user to run `/engineering:execute #<n>` again.
     - a single issue: if step 3 opened a draft PR, close it with `gh api -X PATCH repos/{owner}/{repo}/pulls/<pr> -f state=closed`, and read it back with `gh api repos/{owner}/{repo}/pulls/<pr>` to check that its `state` is `closed`. Open no PR, because its branch becomes the feature branch. Tell the user to run `/engineering:discuss #<n>`, which turns it into an umbrella issue.
  6. A new domain name that the code needs and that no `Term` decision and no glossary entry covers, or a rename of a domain name: if it passes the gate in `domain-model.md`, add or edit its entry in `docs/glossary.md` in the same PR, as `domain-model.md` says, and name the entry under the PR's `## Deviations`.
- An answer from another session: when a step says to stop and ask, and the answer arrives as a message from another session, such as Autopilot's, instead of from the user, go on from that answer as if the user gave it. Record it in the PR under `## Deviations` as one line, `Autopilot: <question> → <answer>, because <why>`, with the question you asked, the answer the message gave and the reason it gave, so the user reads the answer at review. One line for each such answer.

## Steps
1. **Load.** Read `${CLAUDE_PLUGIN_ROOT}/references/size-test.md`, `${CLAUDE_PLUGIN_ROOT}/references/issue-tracker.md` and `docs/agents/commands.md`. Run `gh api repos/{owner}/{repo}/issues/<n>`, `gh api repos/{owner}/{repo}/issues/<n>/parent` and `gh api 'repos/{owner}/{repo}/issues/<n>/dependencies/blocked_by?per_page=100'`. Stop and say why if the issue is closed or has no `## Scenarios` or `## Verify` section. Read `${CLAUDE_PLUGIN_ROOT}/references/domain-model.md` every time, not only when a term comes up, and follow its `In execute` section. Read `${CLAUDE_PLUGIN_ROOT}/references/adr.md` every time too, not only when the issue has an `ADR` decision, and follow its `In execute` section.
   - **Repo profile:** if the repo has no `docs/agents/commands.md`, tell the user to run `/engineering:setup`, which writes it, and go on with the issue's Verify command as the only check.
   - **Base:** for a sub-issue, the parent's feature branch: the one branch that `git ls-remote --heads origin 'refs/heads/<parent>-*'` lists, by the branch pattern in `references/issue-tracker.md`. Stop if it lists none, or more than one. For a single issue, `main`, the default branch.
   - **Blockers:** read the issue's blockers, and their state, from its `dependencies/blocked_by` links only. If an open issue blocks a single issue, stop. If one blocks a sub-issue, list the merged PRs into the base with `gh api 'repos/{owner}/{repo}/pulls?base=<base>&state=closed&per_page=100' --jq 'length, (.[] | select(.merged_at) | {number, body})'`, page by page as the rules say. A repo without the close-sub-issue workflow leaves a merged sub-issue open, so an open blocker counts as merged when a merged PR's first line names it as its issue ("Sub-issue #<b> of" or "for #<b>"). A mention elsewhere in a body does not count. Name each such PR and go on. Stop and name each open blocker that has no such PR.
   - **Terms:** the issue's `Term` decisions are its own `D<n> · Term:` lines, and each `#<umbrella> D<n>` line in its `## Decisions` whose decision in the umbrella is a `Term` decision. Read that decision's text in the body that the `/parent` call returns.
   - **ADRs:** the issue's `ADR` decisions are its own `D<n> · ADR:` lines, and each `#<umbrella> D<n>` line in its `## Decisions` whose decision in the umbrella is an `ADR` decision. Read its text in the same body.
2. **Worktree.** Run `git rev-parse --abbrev-ref HEAD`, `git rev-parse --absolute-git-dir`, `git rev-parse --path-format=absolute --git-common-dir`, `git status --porcelain`, `git rev-list HEAD --not --remotes`, `printenv CLAUDE_CODE_REMOTE` and `git ls-remote --heads origin 'refs/heads/<n>-*'`, which lists the issue's branch. The session is in a worktree when the git dir and the common dir differ.
   - **Sync:** the cases below that say "sync" run these on the issue branch `<branch>`:
     1. Run `git fetch origin <base> <branch>`. If it fails, for example because `<branch>` is not on the remote, stop and ask.
     2. Run `git rev-list --left-right --count HEAD...origin/<branch>`, which counts the commits only on `HEAD` and only on `origin/<branch>`. If they have diverged (both counts above 0), stop and ask. If `HEAD` is behind `origin/<branch>`, run `git merge --ff-only origin/<branch>`, and stop and ask if it fails.
   - **In a session with a designated branch it must push to** (a Claude Code cloud session names one in its system prompt): that branch is the issue branch, and the cases after this one do not apply. Enter no worktree and create no `<n>-<slug>` branch. Stop if `HEAD` is not on the designated branch. List its open PR with `gh api 'repos/{owner}/{repo}/pulls?head={owner}:<branch>&state=open&per_page=100'`.
     - **An open PR whose first line names #<n>** ("Sub-issue #<n> of" or `Closes #<n>`): resume. Stop and ask if the PR's base is not `<base>`. Sync as above. Then read `git log --oneline origin/<base>..HEAD` to see what is done.
     - **No open PR, with no changes and no commits that are not on a remote:** start the branch at the base, so the PR holds only this issue's work. Run `git fetch origin <base>`. If `git ls-remote --heads origin 'refs/heads/<branch>'` lists the branch, run `git fetch origin <branch>`, and stop and ask if `git log --oneline origin/<base>..origin/<branch>` shows commits. Then run `git reset --hard origin/<base>`.
     - **Anything else** (an open PR for another issue, changes, or commits that are not on a remote): stop, show what the branch holds, and ask.
   - **In a cloud session with no designated branch, not on the issue's branch:** enter no worktree, and the cases after this one do not apply. `HEAD` can be detached or on any other branch.
     - **No changes and no commits that are not on a remote:**
       1. If `git ls-remote` lists no branch for the issue, create `<n>-<slug>` from `<base>` as the rules say, with the branch pattern from `references/issue-tracker.md`.
       2. Sync as above, and run `git switch <branch>` between its fetch and its count. If `git ls-remote` listed the issue's branch, then read `git log --oneline origin/<base>..HEAD` to see what is done.
     - **Anything else** (changes, commits that are not on a remote, or a `git switch` that fails): stop, show what the checkout holds, and ask.
   - **On the issue's branch:** resume. Sync as above. Then read `git log --oneline origin/<base>..HEAD` to see what is done.
   - **Not in a worktree, locally:** enter a new one with the EnterWorktree tool, then go on as in the next case.
   - **In a worktree on its own new branch (Remote Control names it `worktree-…`), with no changes and no commits that are not on a remote:**
     1. If `git ls-remote` lists no branch for the issue, create `<n>-<slug>` from `<base>` as the rules say, with the branch pattern from `references/issue-tracker.md`.
     2. Sync as above, and run `git switch <branch>` between its fetch and its count. A local `<branch>` that already existed can be behind, and the count finds that. Then run `git branch -D <the worktree's old branch>`.
     3. Ask the user to name the session with `/rename <branch>`.
   - **In a worktree on `<base>`, the feature branch from step 1, with no changes and no commits that are not on a remote:** this happens after discuss turned a single issue with work so far into an umbrella, because the issue's own branch became the feature branch. Go on as in the case of a worktree on its own new branch, but skip its `git branch -D`: the feature branch is not a throwaway branch.
   - **Anything else** (changes, commits, another issue's branch, or a `git switch` that fails): stop, show what the worktree holds, and ask.
3. **Implement.** Read the code that the Files section names. Work one scenario at a time, and commit as you go with messages that say what changed and why. After the first commit, run `git push -u origin <branch>`, and if the branch has no open PR (`gh api 'repos/{owner}/{repo}/pulls?head={owner}:<branch>&state=open&per_page=100'`), open the draft PR right then, as in step 5, with the same title, first line, base and read-back. Its body is the first line and the line "execute rewrites this body at its PR step." From then on the issue reads as in progress, and step 5 rewrites the PR. Follow the deviation rules. Write each `Term` decision into `docs/glossary.md` as `domain-model.md` says. The Glossary section at the end of this skill holds the file as it was when the skill loaded, and step 2 can switch or update the branch after that, so read `docs/glossary.md` on the issue branch, if it exists, before you judge that no entry covers a name, and before you write an entry. Write each `ADR` decision into `docs/adr/` as `adr.md` says. Read `docs/adr/` on the issue branch first, for the same reason.
4. **Check.** Run the issue's Verify command and each pre-PR check: each row of `docs/agents/commands.md` whose task ends with `(pre-PR check)`, and no other row. If `commands.md` has no such row, or does not exist, run only the Verify command. If one fails, go back to step 3.
5. **PR.** Run `git push -u origin <branch>`. If the branch has no open PR yet (`gh api 'repos/{owner}/{repo}/pulls?head={owner}:<branch>&state=open&per_page=100'`), run `gh api -X POST repos/{owner}/{repo}/pulls -f title="<issue title>" -f head=<branch> -f base=<base> -F draft=true -F body=@<path>`. If it has one, as after step 3's first commit or after deviation 5, rewrite its title and body with `gh api -X PATCH repos/{owner}/{repo}/pulls/<pr> -f title="<issue title>" -F body=@<path>`. Write the body to a file as the rules say. Read the PR back with `gh api repos/{owner}/{repo}/pulls/<pr>`, and stop if its base is not `<base>`, it is not a draft, or its title or body is not the one you wrote. The body has:
   - a first line: for a sub-issue, "Sub-issue #<n> of #<parent>. This PR goes into `<base>`, so it has no `Closes` line."; for a single issue, `Closes #<n>`;
   - `## What it delivers`: one bullet for each change, each naming the decision it serves (`D<n>` or `#<umbrella> D<n>`) or the scenario it makes pass. Do not list the changes per file;
   - `## Deviations`: only if a deviation rule was used or a question was answered from another session, one line for each: the deviation, or `Autopilot: <question> → <answer>, because <why>` for an answer from another session, as the rules say.
6. **Hand off.** Call the Skill tool with `engineering:verify` and the PR number.
   - **FAIL:** fix each gap and each failed check that its report names, and go back to step 4. If it fails a second time, stop and ask.
   - **PENDING:** name each pending check. A PENDING verdict does not count as one of the two failures. Then, the first that applies:
     - **In a cloud session, with a resume left:** the session is a cloud session (step 2's `printenv CLAUDE_CODE_REMOTE` printed `true`), and the arguments carry no `PENDING resume <k> of 3` or carry one with `<k>` below 3; `<k>` is 0 when they carry none. Call the `send_later` tool with `delay_minutes` 10, the name `execute #<n>: PENDING resume <k+1> of 3` and the message `/engineering:execute #<n> PENDING resume <k+1> of 3`. Say that the run resumes itself in 10 minutes, and end the turn. The message starts a run in this session that resumes on this branch and calls verify again, and its arguments carry the count, so at most three resumes follow one PENDING verdict after another.
     - **Otherwise** (not a cloud session, or the third resume got PENDING): stop. Tell the user to run `/engineering:execute #<n>` again once CI has finished. That run resumes on this branch and calls verify again.
